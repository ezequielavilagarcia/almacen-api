# Layer Responsibilities

This document explains the responsibilities of different layers in the NestJS GraphQL application architecture.

## Architecture Overview

The application follows a layered architecture pattern with clear separation of concerns:

```
Client Request → Resolver → Service → Repository (Prisma) → Database
```

## Layer Responsibilities

### Resolvers

Resolvers are responsible for:

- Handling GraphQL queries, mutations, and subscriptions
- Input validation using DTOs and validation pipes
- Authorization checks using guards
- Delegating business logic to services
- Transforming service responses into GraphQL responses

Example:

```typescript
@Resolver(() => User)
export class UserResolver {
  constructor(private userService: UserService) {}

  @Query(() => User)
  @UseGuards(GqlAuthGuard)
  async user(@Args('id') id: string): Promise<User> {
    return this.userService.findById(id);
  }

  @Mutation(() => User)
  async createUser(@Args('createUserInput') createUserInput: CreateUserInput): Promise<User> {
    return this.userService.create(createUserInput);
  }
}
```

### Services

Services are responsible for:

- Implementing business logic
- Coordinating data access through repositories
- Handling domain-specific operations
- Transaction management
- Error handling and domain validations
- Integrating with external services

Example:

```typescript
@Injectable()
export class UserService {
  constructor(private prisma: PrismaService) {}

  async findById(id: string) {
    return this.prisma.user.findUnique({
      where: { id },
    });
  }

  async create(data: { email: string; password: string; firstName?: string; lastName?: string }) {
    const hashedPassword = await this.hashPassword(data.password);

    return this.prisma.user.create({
      data: {
        ...data,
        password: hashedPassword,
      },
    });
  }

  private async hashPassword(password: string): Promise<string> {
    const salt = await bcrypt.genSalt();
    return bcrypt.hash(password, salt);
  }
}
```

### Data Transfer Objects (DTOs)

DTOs are responsible for:

- Defining the structure of input data
- Validating input data using class-validator decorators
- Documenting the API contract
- Providing type safety

Example:

```typescript
@InputType()
export class CreateUserInput {
  @Field()
  @IsEmail()
  @IsNotEmpty()
  email: string;

  @Field()
  @IsNotEmpty()
  @MinLength(6)
  password: string;

  @Field({ nullable: true })
  @IsOptional()
  firstName?: string;

  @Field({ nullable: true })
  @IsOptional()
  lastName?: string;
}
```

### Models

Models (generated by Prisma and prisma-nestjs-graphql) are responsible for:

- Defining the structure of database entities
- Defining the structure of GraphQL output types
- Providing type safety for database operations

Example (auto-generated):

```typescript
@ObjectType()
export class User {
  @Field(() => ID)
  id: string;

  @Field()
  email: string;

  @Field({ nullable: true })
  firstName?: string;

  @Field({ nullable: true })
  lastName?: string;

  @Field()
  isActive: boolean;

  @Field()
  createdAt: Date;

  @Field()
  updatedAt: Date;
}
```

### Guards

Guards are responsible for:

- Authentication and authorization
- Protecting routes/resolvers based on user roles or permissions
- Extracting and validating tokens

Example:

```typescript
@Injectable()
export class GqlAuthGuard extends AuthGuard('jwt') {
  getRequest(context: ExecutionContext) {
    const ctx = GqlExecutionContext.create(context);
    return ctx.getContext().req;
  }
}
```

### Decorators

Custom decorators are responsible for:

- Extracting and providing contextual data to resolvers
- Simplifying common patterns

Example:

```typescript
export const CurrentUser = createParamDecorator((data: unknown, context: ExecutionContext) => {
  const ctx = GqlExecutionContext.create(context);
  return ctx.getContext().req.user;
});
```

## Best Practices

1. **Single Responsibility**: Each layer should have a single responsibility
2. **Dependency Injection**: Use NestJS dependency injection for loose coupling
3. **Thin Resolvers**: Keep resolvers thin and delegate business logic to services
4. **Rich Services**: Services should contain the business logic
5. **Validation in DTOs**: Use class-validator decorators in DTOs for input validation
6. **Proper Error Handling**: Handle errors at the appropriate layer
7. **Clear Boundaries**: Maintain clear boundaries between layers
